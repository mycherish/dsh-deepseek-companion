## 目标与执行顺序

1. 可行性门禁：在全新隔离目录手动登录；顺序关闭可见 context，再用同目录以完整 Chromium 的无界面模式启动。只验证本轮测试会话的文本增量、图片、历史、Stop 与一次后台恢复；不删除远端会话。若实际失败先分析原因，不直接扩大范围或改走 Desktop。
2. RED→GREEN 实现：启动插件只注册服务，不创建浏览器；打开 Chat Buddy 时通过显式请求单飞启动后台实例。模式切换全程只拥有一个 context，完成旧实例 dispose 后再复用同一目录；退出或迟到创建均须清理。
3. 登录：仅用户点击“登录／重新登录”才创建／显示可见窗口；提供“完成登录，返回聊天”操作。未登录、登录失效和故障均只在插件提示，不自动打开可见窗口；用户关闭登录窗口不得触发可见恢复循环。
4. 安全：发送、停止中的轮次、页面切换或附件草稿存在时拒绝模式切换；不自动重发；维持会话身份与现有恢复语义，intentional 模式切换不伪装成 crash recovery。并发、迟到回调和同目录占用使用单飞和世代门控。
5. 工程门禁与审核：按 AGENTS 顺序执行 format:check、lint、typecheck、build、test、diff --check、status／diff，再 test:ui。复审并同步记录，停止等待 Review，不自动提交本轮浏览器改动或发布。

## 实现边界

先给核心浏览器增加显式运行模式（背景／登录）选项，恢复沿用当前实例模式；无界面使用 channel=chromium，复用已安装完整浏览器，不依赖此前未安装的 headless shell。Host 的生命周期协调独立于 DOM 聊天实现，保留 API 前缀、profile 路径、消息身份和恢复预算。状态读取／SSE 不触发创建；Client 首次打开显式激活。新增生命周期投影保持旧 Host 状态兼容，登录转换可见且可理解。

优先复用现有客户端、状态存储、page guard 和 browser engine；仅在真实验证通过后实现协调与 UI 接线。本轮不兼容 Desktop，不改变正式版本／线上市场／网站。

## 第 6 小步：最终代码审核（发现一项 Medium，待修）

**[Medium] 返回后台时的会话对齐被模式切换锁跳过。**

- 位置：src/host/browser-session.ts:65、src/host/browser-session.ts:56 与 src/index.ts:193。
- 调用链：模式切换 run() 先 claim 页面锁；replace('background') 在锁内 await created.check()；check() 的 initialRestore 调用 onSettled → runReconcile；runReconcile 再次 tryClaim 同一非重入锁，必定返回 false。
- 影响：登录窗口期间原会话在服务端发生变化时，返回后台不会读取并对齐该会话的最新内容；clearSessionUnverified 又发生在锁申请之前，可能先恢复发送能力。initialRestore 已 markKnown 并抑制导航同步，release() 的 sessionSync.drain() 不会补做本次对齐。窗口能正常隐藏并不证明会话对齐已执行。
- 复核：使用实际 createBrowserSession 与 createPageGuard 的本地模拟，check 回调内 tryClaim=false，转换结束后锁已释放。未访问真实站点、未新增开发。
- 最小修复方向：让恢复后的对齐复用已持有的转换锁，或在旧锁释放后安排一次受保护的对齐；保持单实例、发送隔离和既有严格身份规则。补一条覆盖“模式切换→initialRestore→实际对齐”的组合回归即可，不重跑真实聊天全矩阵。
